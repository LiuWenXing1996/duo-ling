# 0042. 注释密度增量门禁：只算暂存新增行、只拦偏高

日期: 2026-10-18
状态: 已接受
代码落点: scripts/check-comment-diff.mts（文件头指针指回本文件）；注释判定与全仓口径共用 scripts/lib/comment-scan.mts

## 背景

全仓 ratchet 基线挡的是注释总量缓慢上涨，但一次几十行的提交摊进几万行里看不出来。要抓「本次往代码里塞了一大段注释」，只能按增量算。

增量口径有两个天然陷阱：

- 按整个文件算，改一行也会把文件其余部分拉进分母，数字与本次改动无关；
- 小样本下密度只有两极：新增一行代码是 0%，新增一行注释是 100%。设下限等于逼人给每个小改补注释。

## 决策

- **只算新增行**：分子分母都取「本次暂存新增且非空」的行；未改动行只参与注释判定，不进计数。
- **统计范围**：`.ts` / `.mts` / `.vue` / `.js` / `.mjs` / `.css` / `.less` / `.yml` / `.yaml` / `.html`，含 `.d.ts` / `.d.mts`。`.md` 是文档、`.json` 没有注释语法，两者不参与；`pnpm-lock.yaml` 排除 —— 它由工具生成、近万行，计进来密度只反映依赖数量；`dist` 与 `node_modules` 照旧跳过。
- **只拦偏高，阈值随新增量递减**：新增非空行超过 20 后才判定，阈值从 10% 起，每满 10 行降 0.5 个百分点，到 1% 封底（新增 200 行及以上一律按 1%）。起点给到 10% 是因为小改动样本太小 —— 25 行里写两行注释就已 8%，按 1% 判等于不许解释；大块新增才有足够样本谈比例，越接近全仓 target 越该收紧。
- **读暂存区**（`git show :file`）而不是工作区文件：工作区里可能还有没 add 的改动，读文件会把它们算进来。
- **注释判定交给解析器**：ts / js 用 `typescript` 的 token 注释区间，`.vue` 拆块后 script 走 `typescript`、template 与 `.html` 走 `parse5`、style 与 `css` / `less` 走 `postcss`、`.yml` 走 `yaml` 的 CST token。正则字面量、模板串里的嵌套、YAML 引号内的 `#` 都由语法层判定，不靠字符猜。
- **不进 CI 的 `verify`**：CI 里没有暂存区，`git diff --cached` 为空，暂存模式搬进去恒过；总量兜底由全仓基线承担。PR 级增量判定是另一条路，见下方「PR 级模式」。

阈值以千分比整数参与比较（`注释 × 1000 > 阈值千分比 × 非空`），正好压在阈值上放行 —— 新增 100 行里 6 行注释、阈值 6%，不拦。

## 备选与否决

- **按文件算密度**：改一行就把整个文件计入，数字与本次改动无关。
- **拦偏低（逼着写注释）**：小样本下误报率极高，且会诱导凑数注释 —— 密度本身可被一行 `// 更新` 污染。
- **按单文件判定**：一个文件 500 行 30% 注释、另一个 1000 行 0%，按文件看两边都「合规」，按总计才反映这次提交整体往哪走。
- **手搓字符级状态机**：正则字面量里的 `//` 会误判成注释、模板串 `${}` 内的注释会漏算；而且密度与卫生两道门禁各有一份副本，已经漂移出过一次同步缺陷。
- **暂存模式整体搬进 CI**：无暂存区可读，只会恒过（按合并增量判定的 PR 级模式见下节，不受此限）。

## 代价与后果

- 新增文件的长文件头会直接计入分子，所以长说明落 ADR，代码里只留一两行指针 —— 与 ADR 的既有分工一致。
- 「删注释、留代码」这类动作在增量口径里看不到（只有一个删除 hunk，分子分母都空），仍由全仓基线兜。
- **分不清「给代码补注释」与「修整既有注释」**：折行超宽注释、去掉小节号这类提交新增行全是注释，比例必超上限。这类提交只能带 `LEFTHOOK=0` 提交并在 PR 说明，全仓基线仍兜总量。
- 全仓基线有 `--update` 这个合法出口，增量门禁没有：被拦只能改注释或精简，绕行手段是 `LEFTHOOK=0`，与其它 pre-commit 钩子相同。
- 依赖 `parse5` / `postcss` / `postcss-less` / `yaml` 四个解析器，每个文件都要跑一次 AST 解析 —— 561 个文件约 1 秒，仍在 pre-commit 可接受范围。

## PR 级模式（`--base`）

pre-commit 按单次暂存判定，把一次大提交拆成每批 ≤20 行的分批提交即可绕过 —— 逐提交的口径对提交粒度敏感，这是它补不上的洞。补一个 PR 级模式：CI 的 Gate job 在 PR 事件上跑 `check:comment-diff --base origin/<base_ref>`，把整个分支相对 merge-base 的合并增量算一次，分批提交合到一起仍超阈值，绕过失效。同一脚本、同一套阈值公式，只是 diff 的取数来源不同：

| | 暂存模式（pre-commit） | PR 模式（`--base`） |
| --- | --- | --- |
| 文件清单 | `git diff --cached --name-only` | `git diff --name-only <base>...HEAD` |
| 新增行区间 | `git diff --cached --unified=0` | `git diff --unified=0 <base>...HEAD` |
| 文件内容 | `git show :<file>`（暂存区） | `git show HEAD:<file>`（提交树） |

- **三点语法取 merge-base**：PR 存续期间 main 前进不影响判定；`checkout` 相应要 `fetch-depth: 0`，浅 clone（默认 depth=1）算不出 merge-base。
- **只挂 `pull_request` 事件**：push main 与每日定时没有合理的 diff 基点，步骤用 `if` 跳过；本地无 PR 语义同理不跑 —— 故该步骤只写在 ci.yml，不进 `package.json` 的 `ci` 脚本。
- **阈值公式共用**：20 行门槛与递减上限照旧。PR 总量通常远大于单次暂存，多数落在 1% 封底档。
- **无逃生舱**：治理型改动（折行超宽注释、清小节号）新增行全是注释、比例必超上限，pre-commit 的 `LEFTHOOK=0` 在 CI 侧不存在，这是刻意的 —— 门禁防手滑与防分批塞注释，不设可写的绕过标记。新增 ≤20 行的小修整靠门槛天然放行；更大规模的注释治理走全仓基线路径（治理后基线随 `check:comment-baseline` 的自动下调固化，`--update` 只用于抬基线），治理与代码混在同一个 PR 时只能拆成每批新增 ≤20 行的提交。

代价：CI 全量 fetch 一次（仓库体量下无感）+ 每个 PR 多一次 AST 扫描（约 1 秒，同上实测口径）。
