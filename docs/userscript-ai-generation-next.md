## 归属论证：为什么是三案

判据：**一件事 = 一个能独立说清「改完了没」的变更**；同一份文件 + 同一套验收方式 → 不再拆；必须同时改才自洽的两半 → 不许拆。

- **提案 ①「元素拾取器」单独成案**（现已落地）：它跨四层（内置脚本项目 → 侧边栏拾取入口 → 回传通道选型 → 载荷形态），验收是「用户点选元素后，AI 拿到真实选择器与同类计数」——与其余各项没有交集；最终回传走 `execute()` 返回值、**DL 桥零改动**，与只动 offscreen / UI 的 ② 不同批文件。**#10 档 1 / 档 3 页面探针同属「页面上下文」这一面，并入本批**（档 1 落地为 `page_snapshot` 工具、档 3 不做）；**#6「内置」分组也归这一案（切法 A）**（它是拾取器的前置；两种切法见下节）。
- **提案 ②「生成体验完善」**（#2 进度通知 / #3 消息排队 / #7 regenerate / #8 推送实测）：#9 运行期反馈闭环已随 PR #25 落地（见 `proposals/done/runtime-feedback-loop.md`），剩余四项同批验收更省；#8 是实测项（结论可能是「不用改」），与其余三项同属一次体验打磨，合批验收。
- **提案 ③「脚本资产流转」**（#4 zip / #5 notes）：内聚不是「文件相同」，而是**都在扩展脚本库这个资产面上——进出的通道（zip）、档案（notes）**，验收方式同为「列表 / 管理页的可观察结果」；#4 已有定稿方案、#5 是小增量，同批可一次把管理页口径理顺。
- **不合成一案**：十项里有三项（#1 拾取器、#4 zip、#8 实测）各带独立前置决策（回传通道选型、`fflate` 依赖、是否换通道），合成一案会让验收标准无法逐条勾选，也违反「一个 PR 装不下就拆提案」。

## #6「内置」分组的归属

| 切法 | 主张 | 代价 |
| --- | --- | --- |
| **A. 整项归「元素拾取器」提案**（架构师的判定） | 「内置」这个概念是为拾取器引入的（zip / notes 都不需要它），且它是拾取器的**前置**——跨提案前置会把拾取器卡住 | ① 的验收面从「AI 拿到真实选择器」扩到「管理页出现内置分组」，① 变大（但仍在「能独立说清改完了没」的范围内） |
| **B. 拾取器只带最小承载，完整分组体验归「脚本资产流转」提案**（本路线图起草时的建议） | ① 保持最小（只做拾取器功能上必需的承载）；完整分类体验与 zip / notes 同属管理页资产面，同批做省一次改动 | 「内置」概念在 ① 里以「最小承载」先行落地，等于跨提案前置的一半——读者要读两个提案才知道内置脚本最终长什么样；且若 ③ 迟迟不做，管理页会长期只有一个半成品分组 |

**分歧点**：#6 算「① 的组成部分」还是「③ 的组成部分」——实质是**要不要为了「不把前置拆到两个提案」而接受 ① 变大**。

**结论：切法 A**——跨提案前置本身是风险，切法 B 的收益「省一次管理页改动」不足以抵。代价一并认下：**① 的验收面从「AI 拿到真实选择器」扩到「管理页出现内置分组」**；若担心 ① 过大，把「内置」分组的**完整 UI 体验**作为 ① 内部的可选后置项，仍留在 ① 里，不拆去 ③。上表两种切法与各自代价并列留档。
