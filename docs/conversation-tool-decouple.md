# 会话与工具解耦 · 方案

> 设计文档 · 已进入实施
>
> 核心诉求：把「会话/对话」从「强绑定工具」提升为**一等公民（first-class entity）**，与工具解耦。同一会话可修改任意工具，甚至一次修改多个工具；支持多个 AI 会话并行思考、但对同一工具的写入天然串行、可控、可回滚。本文档为方案定稿；实际落地进度与待补缺口见 [todo.md](./todo.md)「会话与工具解耦」条目（P1 基本落地、P2 部分、P3 未实现）。

## 01 定位与目标

- 会话是**一等公民**，不再从属于任何工具；一个会话可以零工具存在（纯聊天），也可以改任意多个工具。
- 「改哪个工具」不再由会话绑定决定，而是由**每次变更（EditIntent）**决定。
- 目标：像人的工作台一样——一次对话可以随手修好几个工具，AI 之间可以并行讨论，但对同一工具的写入天然串行、可控、可回滚。

## 02 核心数据模型

```
Conversation { id, title, createdAt, lastMessageAt }
Message      { id, conversationId, role, content, createdAt }
EditIntent   { id, messageId, toolId, summary, actions[], status }
Tool         { id, ... }   // 磁盘目录，独立于会话
```

关键点：

- **会话从不拥有工具**。`Conversation` 与 `Tool` 之间没有直接关联，唯一关联是通过 `EditIntent.toolId`。
- 一个 `EditIntent` 只指向**一个**工具；一次多工具修改 = 一条消息下挂**多个** `EditIntent`。
- `actions[]` 是落到具体文件/工具页的操作描述（见 §3）。

对应到既有代码：主进程已有 `store.ts`（tasks）+ `chat-store.ts`（按 taskId 分桶消息）+ `chat.ts` 管线。这套可升级为「Conversation 独立存储 + 消息 + EditIntent 关联表」，把「任务」概念替换成更通用的「会话」。

## 03 AI 契约（多工具 manifest + 只读锁查询）

AI 输出不再假设「当前打开一个工具」，而是显式声明要改哪些工具：

```json
{
  "intents": [
    { "toolId": "read-file-preview", "summary": "给 A 加导出按钮",   "actions": [...] },
    { "toolId": "md-render",          "summary": "给 B 加暗色模式", "actions": [...] }
  ]
}
```

同时给 AI 增补**只读能力**（不拿锁，可任意并发调用）：

- `tool.lock.status(toolId)` → 查询某工具当前是否被持有、被谁持有。

这样 AI 在**规划阶段**就能自检，而不是靠宿主猜测。

## 04 无感确认 = 事后可逆，不是事前阻塞

- 前置「弹窗确认」取消，改为**执行 + 全程可撤销**。
- 靠 **git 版本化 + `tool.rollback`** 兜底：**每个 EditIntent 一个 commit**，撤销 = `revert` 到父 OID。
- 「无感」的代价是「可感知」——用户能看到**每条 EditIntent 作为一个可独立撤销的变更**，而非一次性大改动。

## 05 并发模型与单写者锁

**总原则：AI 思考/讨论/规划/读取 = 并发无锁；AI 写工具 = 按工具全局锁串行。**

- **锁**：主进程按 `toolId` 为 key 的全局锁，覆盖所有写路径（AI 落盘、回滚、meta 编辑、直接文件编辑）。
- **锁带持有者标识**：
  ```
  Lock { toolId, holder: { conversationId, messageId, intentId }, acquiredAt }
  ```
- **查锁（读注册表）永远畅通、不阻塞**；**拿锁（排他写）** 同一 `toolId` 同时只有一个写者。
- 多 AI 编排采用「编排者-工人」模型：一个会话可以是思考中的并行线程，但写工具会走全局锁。

## 06 多个 AI 会话并发访问同一工具（B 方案）

不做并发上限调度器（3-4 个 AI 是用户自然上限）。采用「查-执行」两步，本质是**乐观并发 + 检查后才动作**：

```
AI_X 规划工具A
  ① 查锁(toolA) → 被 AI_Y 持有
  ② 对话提示 → 按 B：跳过该工具 + 告知原因，不排进待办
     （提示：「toolA 正被会话Y修改，我先把这条放一边，你可以稍后再派给我」）

执行工具A（用户确认后）
  ③ 拿锁(toolA) → 成功 → 重读重生成 → 落盘 → 释放锁
  ④ 拿锁(toolA) → 失败（被 AI_Y 抢先）→ 执行失败
     （提示：「toolA 执行失败：该工具正被会话Y占用，无法获取写入锁」+ 可重试出口）
```

- **规划撞锁** → 跳过 + 提示（B）。
- **执行撞锁** → 视为失败 + 告知原因 + 提供「等待释放后重试」。

## 07 执行管线：待办清单 + 逐工具串行

- 清单**只展示意图（intents）**，是展示型清单，不是一次性批量执行。
- 执行时**一次改一个工具，每改一个锁一个工具**。
- **锁前提示**：告知用户「此工具后面将于何时被 AI 锁定，请勿操作」。
- **重读重生成（Plan B 的核心）**：持锁后**重读当前内容**再重新生成，而非直接套用规划时的快照。好处：
  - 不覆盖用户在此期间的手动修改；
  - 能识别「已无需改动」的情况并同步告知用户（此时该条可标记为「跳过」）。

## 08 执行期间的中断

采用业界主流（v0 / Bolt / Lovable / ChatGPT / Claude）的做法：

- **执行期间禁止发新消息**，输入框换成「停止」按钮。
- **优雅中断**：收尾当前项 → 释放锁 → 取消剩余项 → 恢复输入。
- 中断不丢已完成的提交（git commit 已落库，可单独撤销）。

## 09 数据区边界

- 数据区：`<userData>/tools-data/<id>/`，与工具源码 `<userData>/tools/<id>/` **分离**。
- 每个 key 独立 `<key>.json` + `manifest.json`，**单 key 原子**；无跨 key 事务。
- `normalizeKey` 白名单 `/^[A-Za-z0-9_-]+$/`，防目录穿越。
- **AI 不写数据区**（数据区是工具的内部资源，由工具页自己读写）。
- **不锁数据区**——因为它是独立资源、单 key 原子、AI 根本不写。真正的风险是**语义/版本漂移**，用「schema 版本 + 读容错」解决，而非并发锁。

## 10 webview 重写编排

- 工具页是 `<webview>`，重写时：**停旧页 → 写文件 → 加载新页**。
- 用**「过渡占位」**而非遮罩/白屏：只在「写文件 → reload」这个短暂窗口出现占位。
- **批量写 + 单次 reload**；多工具则逐个工具占位。
- 复用现有 `reloadFrame()`（`tool-frame.vue`）与心跳 watchdog（guest preload 每 2s 发 `__duo_ling_heartbeat__`）判断卡死。

## 11 边界与例外

| 场景 | 行为 |
| --- | --- |
| 规划撞锁 | 跳过 + 提示（B） |
| 执行撞锁 | 失败 + 告知原因 + 重试出口 |
| 用户手动改了工具 → AI 落地 | 持锁重读重生成，识别并同步「已无需改动」 |
| 执行中用户想介入 | 禁发新消息 + 停止按钮，优雅中断 |
| 中断后 | 当前项收尾提交、释放锁、取消剩余、恢复输入 |
| 数据区版本漂移 | schema 版本 + 读容错，不锁 |

## 12 建议分阶段落地

- **Phase 1（解耦与契约）**：会话独立存储 + EditIntent 模型 + 多工具 manifest + 只读锁查询能力。
- **Phase 2（执行管线）**：待办清单 + 逐工具串行 + 锁前提示 + 重读重生成 + 优雅中断。
- **Phase 3（并发协调）**：per-tool 全局锁（带持有者）+ 查-执行两步 + 失败重试。
- **数据区 + webview 编排**可并行推进（相对独立）。
