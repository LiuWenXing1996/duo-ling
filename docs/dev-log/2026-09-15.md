## API Key 存储方案（三轮迭代后的终态：静默加密落盘）

一天内三易其稿：明文 → 口令保险库（实现后撤）→ **静默加密**（终态）。
老大先拍板撤保险库，随后要求「好歹加密下」，最终定为不引入口令的
AES-GCM 静默加密，用户完全无感。

终态实现：

- `src/lib/key-cipher.ts`（新）：安装期首次使用时生成 32 字节随机密钥
  （`chrome.storage.local` 的 `apiKeyDek`，base64），AES-GCM 加解密，
  同上下文内存缓存；`isEncPayload` 供读取时区分新老形态。
- `src/lib/model-store.ts`：拆「落盘形态 `StoredProfile`（`apiKeyEnc` 密文载荷，
  不再有 `apiKey` 明文字段）/ 内部形态 `ModelProfileState`（恒带明文，仅供
  SW / offscreen 内存使用）」。读路径透明解密；老数据的明文字段在首次读取时
  自动迁移为密文并回写；解密失败（密钥丢失 / 载荷损坏）宁缺勿假清空待重填。
- `ModelFormDialog.vue` 提示文案改为「Key 加密后仅保存在本机…」。

**能力边界（务必如实告知用户，已写进 key-cipher.ts 头注释与 README）**：
扩展拿不到系统钥匙串、又不引口令，密钥只能同存本机——此加密为
**防扫描级**（挡备份同步、文件拷走后的明文 grep），**非保密级**（能读到
扩展存储的人就能解密）。对抗本机恶意软件无解，真实降损靠
「子 Key + 额度上限 + 定期轮换」。

## 已放弃的口令保险库方案（留档）

曾完整实现 PBKDF2-SHA256 600k 派生 + `chrome.storage.session` 缓存 DEK 的
口令保险库，老大认为使用门槛不划算而撤销。关键教训留档：

- DEK 不能只放 `chrome.storage.session`（关浏览器即丢，密文永久解不开），
  必须由口令派生；`model-store` 必须拆「落盘 / 内部」两层形态，否则与密钥
  无关的写路径会在锁定态把空串写回去抹掉 Key（终态加密方案沿用了这个分层）。
- 最关键的既有边界是「用户脚本（页面主世界）全链路拿不到 apiKey」，
  后续做 AI 生成脚本时不得为省事把模型配置整包传过去。

## AI 生成用户脚本 · 一期主链路落地（定位 B：整条对话链路搬进 offscreen）

按 docs/userscript-ai-generation.md（已拍板，无待拍板项）实施一期 9 条前置中的
5/6/7/8/9（A 组容器与通道此前已就位）。本次改动分四块：

### 1. 整条对话链路搬进 offscreen（不做任务类型分流）

- 新增 `src/lib/offscreen-chat/`：`chat-host.ts`（编排宿主）+ `event-bus.ts`
  （per-conversation 事件缓冲）+ `task-store.ts`（任务快照）+ `script-tools.ts`
  （Agent 工具）+ `spec-text.ts`（script_spec 载荷）+ `profile-cache.ts`（配置缓存）。
- `chat-host` 里 streamText 带 `tools` + `stopWhen: stepCountIs(8)`（沿用桌面版
  maxSteps）；泵 `toUIMessageStream` 逐 chunk 入缓冲并经 `chat:chunk` 推给侧边栏。
- `extension-chat-transport.ts` 从「渲染层直跑 streamText」改为纯 IPC transport：
  `sendMessages` 只发 `chat:start`，随后把 offscreen 推送收集成 ReadableStream 喂 useChat。
  关面板任务照跑、重开面板接上——定位 B 的体验主契约。
- 会话历史的**唯一写入方 = offscreen**（防双写）：用户消息在 chat:start 时落盘、
  assistant 消息收尾时落盘（含完整 parts 与 usage）；侧边栏只读。为此把会话自增
  序号从 chrome.storage.local 迁进 duoling-chat 库的 meta store（DB_VERSION 2，
  单 readwrite 事务内原子自增；首次取号顺带从旧键迁移），否则 offscreen 建不了会话。
  `window-api` 的 conversation 写命令改经 `conv:*` 路由 offscreen，读仍直连 IndexedDB。
- `data-usage` / `data-generation` 两个 data part 随流推送、随消息落盘，重开面板可还原。

### 2. reconnectToStream 真实现 + lastEventId replay

- offscreen 每条事件带自增 seq；`chat:resume` 按 lastEventId 回放缓冲后续订实时推送。
- **缓冲生命周期是关键决策**：任务收尾（正常 / 中止 / 异常）即删缓冲——缓冲只为
  「进行中任务」的重连服务；收尾后结果已在会话历史，保留缓冲反而会让重开面板
  replay 出重复消息。侧边栏对 seq 去重，replay 与实时推送短暂重叠也安全。

### 3. userscript:createProject + Agent 工具三件套

- `userscript:createProject`（SW 命令面）→ `state:createProject`（offscreen 单写方）→
  `project-write.createGeneratedProject`：写状态库 + git 快照（note = AI summary），
  `enabled: false` 默认不注册——「生成」与「生效」解耦，启用复用现成 `userscript:toggle`。
  offscreen 的 loop 收敛后经 SW 命令面调用（保持落盘入口唯一），不走本地直写捷径。
- `script_spec`（规范全文注入）/ `script_read`（内存树或已存脚本）/
  `script_apply`（整文件写 + esbuild 构建一步完成，失败回 file:line 诊断）。
  连续失败 ≥6 次返回 stop 提示让模型停手抛诊断，是 maxSteps 之外的第二道闸。

### 4. 任务快照 + 孤儿「继续 / 丢弃」+ 生成卡片

- `duoling-chat-tasks` 库（IndexedDB）：每步 apply 成功覆盖写文件树快照，5s 心跳；
  status=running 且心跳 >30s 未跳 = 孤儿（宿主被杀），侧边栏启动时拉 `chat:orphans`
  显示横幅。「继续」= 播种内存文件树 + 从会话历史重建上下文重跑 loop（system 注入
  续跑说明）；「丢弃」= 删记录。收尾 git 快照在落盘函数内完成（全链路唯一非幂等动作）。
- 卡片渲染 `data-generation`：名称 + 未启用徽标 + 生效范围（matches）+ 会做什么
  （bundle 里 DL.* 静态扫描）+ 摘要 + 三出口（启用并生效 / 进编辑器 / 删除）。

### 停止语义（容易踩的坑）

「停止按钮」与「切换会话」必须区分：两者都触发 useChat 的 abortSignal，但切换
不该杀掉 offscreen 里照跑的任务。实现上 transport 的 abortSignal **不**接 chat:abort，
显式停止由 composable 的 stopGeneration 额外调 `transport.abortCurrent()` 发
`chat:abort`。切走再切回 = resumeStream 按 lastEventId 接上。

### 根因修复：长回复冲掉环形缓冲导致 assistant 消息不落盘（同日第三次提交）

警示条带出诊断（complete=false, events=0）→ 确认是环形缓冲截断：23013 tokens
的回复产生 2 万+ delta chunk > 4000 条上限，replaySince(0) 判不完整，还原返回
undefined，落盘被跳过。修复：泵流时自收完整序列（allChunks），收尾还原与
缓冲彻底解耦；卡片/usage data 块插在 finish 前参与还原（进 parts 必须先于
finish）。教训：**为重连设计的缓冲不能挪用作落盘数据源**；容量论证要按最坏
token 量而不是步数。

### 手测「停止」三连修（3fe5591）

1. **停止后落盘半截消息**：abort 后 toUIMessageStream 仍补发 finish → 分支 2

### 手测排查：部分会话标题停在「新会话 N」（24b238f）

DB 实查（用户贴 conversations 表 dump）：9 个会话里 5 个改名成功、3 个
（新会话 7/8/9）停在默认标题——自动命名逻辑本身没坏，是部分时序下没触发。
两个结构性弱点（一并修掉）：

- `appendMessage` 拆 3 个独立事务（查 existing → 写消息 → 读+写会话），
  非原子：两个 append 并发交错时，后提交的会用读到的旧标题把先完成的
  改名覆盖回去。收敛为单 readwrite 事务。
- 命名条件按「没有任何消息」判断：assistant 消息若先落盘（异常收尾、
  半截恢复等），改名静默失效。改为按「此前没有用户消息」判断。

遗留确认：3 个会话的具体触发时序未钉死，待 messages 表 dump（按 conv
过滤 7/8/9 的消息顺序）复核。截图里「你好」的回复内容本身正常——模型
引用上一轮半截消息接话，属预期。

### 手测「切回会话」根因修复：重连从头全量回放（6d62eba）

错误横幅（上一轮修复的成果）终于带出真凶：useChat 报
「reasoning-delta for missing reasoning part（reasoning-start 未发送）」。
两个同根问题：

1. **resume 按消费点续传 vs 本地视图从历史重建**：切回会话时
   activateConversation 先用历史重建消息列表（进行中的半截 assistant
   消息不在历史），reconnectToStream 却带 lastEventId 只回放增量——
   start / reasoning-start 等配对块已在上次消费点之前，永远补不上。
   修复：resume 一律从头回放完整缓冲。缓冲只存当前任务、收尾即删，
   全量回放天然无重复；lastEventId 协议字段移除。
2. **去重基线跨任务保留 vs seq 每轮重计**：offscreen 的 seq 在
   resetBuffer 后从 1 重数，transport 的 lastSeq 却留着上一轮的值——
   同会话第二轮任务开头的配对块被当「重播」丢弃。修复：chat:start
   与重连回放前均清零基线，回放重建基线后与实时推送自然衔接。

缓冲上限 4000→50000（教训复用：按最坏 token 量论证，23013 token
曾冲穿旧上限）；截断时 resume 返回 idle、由会话历史兜底。

### 手测「停止后发闲聊」：模型自动续做脚本（3fcbb03，提示层约束）

停止生成后发「你好呀」，模型回应问候的同时顺手把脚本写完——思考过程
明说：「之前的需求没交付，我回应问候后继续交付」。链路本身正确（旧任务
确被 chat:abort 杀掉、回复属新一轮任务），属模型自主判断；且历史里那条
带中断 script_spec 的半截消息是**修复前落盘的脏数据**（现在停止已不落盘，
此形态不会再新增）。在 system 提示加约束：闲聊只回应，中断的工具调用
是用户主动停止留下的，仅当新消息明确要求才续做。提示级约束非硬保证，
模型不听话时属预期偏差，不按 bug 处理。

### 手测孤儿「继续」：点了没反应，切回才接上（9da3944）

现象链完美指认真凶：任务一直在 offscreen 正常跑（切走再切回，输出全出来），
是面板**首次 attach 失败**。根因：点「继续」→ resolveOrphan 立刻激活会话并
resumeStream，此刻 offscreen 的续跑循环刚起步（取历史 / 连模型），事件缓冲
为空 → reconnectToStream 以 `events.length === 0` 返回 null 放弃 attach →
后续实时推送因无消费者全部落空。切回会话时缓冲已攒到事件，故能接上。

修复：resume 应答 status=running 即建流挂消费者，空缓冲也等实时推送；
仅 idle 返回 null。「切回能接上」属于同一 bug 的非对称表现，一并在
attach 逻辑里修死，不依赖缓冲恰好非空。

顺带：resolveOrphan 的异常原来被模板里的 void 吞掉（失败时横幅消失但
任务记录还在），现写入 chatError 警示条 + 重新拉取孤儿列表。

教训：**「无初始数据」≠「无事发生」**——订阅型接口把「暂无事件」和
「没有任务」混为一谈，就会在快启动场景下静默失联。

### 手测答疑引出的改进：孤儿判定不再等 30 秒（d41485e）

用户问「为什么要等 30 秒」——原判定纯时间-based（心跳 >30s 未跳），
余量防误伤活任务。但更准的判据一直在手边：offscreen 内存中的
runningByConversation 表。记录说 running 而内存表没有 = 宿主换代，
必是孤儿。改为交叉核对后，30s 等待窗缩为 5s（仅盖 chat:start 落盘 →
runLoop 注册的竞态窗口）。另补 15s 轮询让横幅在面板开着时也能自动浮现
（原来只在挂载时检测一次，保护窗内重开就永远看不到横幅）。
