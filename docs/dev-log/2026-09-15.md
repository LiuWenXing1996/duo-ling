# 2026-09-15

## API Key 存储方案（三轮迭代后的终态：静默加密落盘）

一天内三易其稿：明文 → 口令保险库（实现后撤）→ **静默加密**（终态）。
老大先拍板撤保险库，随后要求「好歹加密下」，最终定为不引入口令的
AES-GCM 静默加密，用户完全无感。

终态实现：

- `src/lib/key-cipher.ts`（新）：安装期首次使用时生成 32 字节随机密钥
  （`chrome.storage.local` 的 `apiKeyDek`，base64），AES-GCM 加解密，
  同上下文内存缓存；`isEncPayload` 供读取时区分新老形态。
- `src/lib/model-store.ts`：拆「落盘形态 `StoredProfile`（`apiKeyEnc` 密文载荷，
  不再有 `apiKey` 明文字段）/ 内部形态 `ModelProfileState`（恒带明文，仅供
  SW / offscreen 内存使用）」。读路径透明解密；老数据的明文字段在首次读取时
  自动迁移为密文并回写；解密失败（密钥丢失 / 载荷损坏）宁缺勿假清空待重填。
- `ModelFormDialog.vue` 提示文案改为「Key 加密后仅保存在本机…」。

**能力边界（务必如实告知用户，已写进 key-cipher.ts 头注释与 README）**：
扩展拿不到系统钥匙串、又不引口令，密钥只能同存本机——此加密为
**防扫描级**（挡备份同步、文件拷走后的明文 grep），**非保密级**（能读到
扩展存储的人就能解密）。对抗本机恶意软件无解，真实降损靠
「子 Key + 额度上限 + 定期轮换」。

## 已放弃的口令保险库方案（留档）

曾完整实现 PBKDF2-SHA256 600k 派生 + `chrome.storage.session` 缓存 DEK 的
口令保险库，老大认为使用门槛不划算而撤销。关键教训留档：

- DEK 不能只放 `chrome.storage.session`（关浏览器即丢，密文永久解不开），
  必须由口令派生；`model-store` 必须拆「落盘 / 内部」两层形态，否则与密钥
  无关的写路径会在锁定态把空串写回去抹掉 Key（终态加密方案沿用了这个分层）。
- 最关键的既有边界是「用户脚本（页面主世界）全链路拿不到 apiKey」，
  后续做 AI 生成脚本时不得为省事把模型配置整包传过去。

## 层 3 构建冒烟落地（vitest 基建顺带就位）

测试体系第一次有了可跑的测试：`vitest.config.ts`（`WxtVitest()` 插件 + node 环境，
只收集 `src/**/*.test.ts`）、`npm run test` 脚本、首份测试
`src/lib/userscripts/builder.test.ts`（最小项目构建出 IIFE / 入口缺失 / 模块解析
失败三例，全部经真实 esbuild-wasm wasm 编译）。

**核心结论（常青，详见 testing-plan「层 3 实施结论」）**：esbuild-wasm 的 node 入口
（`lib/main.js`）根本不跑 wasm 而是 spawn 原生二进制，`initialize({wasmURL})` 直接抛
「only works in the browser」；真正的 wasm 在 `lib/browser.js`，node 下唯一走通姿势是
`wasmModule`（内存编译字节）+ `worker: false` + stub `self = globalThis`——worker
模式要 Blob/createObjectURL/Worker，主线程分支的 wasm 引导要从 `self` 原型链重建
globalThis，且 `fetch(wasmURL)` 不支持 file://。测试用 `vi.mock` 拦截 initialize 完成
这组转换，`builder.ts` 本体零改动，offscreen 行为不变。

坑：esbuild-wasm 是 UMD 包，`import` 具名导出检测不可靠，mock 里要用
`createRequire` 拿 `module.exports`；测试内 `stubGlobal(...)` 后紧跟 `(` 开头的语句
会被 ASI 拼成函数调用（`vi.stubGlobal(...) is not a function`），要补分号。

## E2E 冒烟开通（层5 全绿 + 首跑抓到一个真 bug）

`npm run test:e2e` 开通：`@playwright/test` + 捆绑 Chromium（channel: 'chromium'，全程无头），
跑 `npm run build` 产物，6/6 通过（SW 命令面 / offscreen:ensure / userScripts 引导 /
workbench / sidepanel / 脚本注入 + DL 桥往返）。方案、结论与坑的全文见
[testing-plan.md](./testing-plan.md)「E2E 已落地」，要点：

- **userScripts 无头可用**：`developerPrivate.updateProfileConfiguration` 开全局开发者模式 +
  在详情页点「允许运行用户脚本」cr-toggle（无 UI，Playwright 穿透 shadow DOM 点击）+ 重启
  扩展上下文，`chrome.userScripts` 即可用。`updateExtensionConfiguration({ userScriptsEnabled })`
  在 Chromium 153 已不存在该字段（报 Unexpected property），网上流传的 API 姿势不可信。
- **chrome://extensions/?id= 直达参数在无头下不触发 SPA 路由**，必须点「详情」按钮进详情页。
- **SW 不能给自己发 runtime 消息**（不回环），命令面测试要从扩展页发（fixture 开 sidepanel
  当发送端）。
- **抓到真 bug 并已修**：MV3 默认 extension_pages CSP 不含 `'wasm-unsafe-eval'`，
  offscreen 里的 esbuild-wasm 必挂——v2 方案 §Phase 2「默认已含、无需改 manifest」的论断
  有误（已在该文档标注勘误）。修法：`wxt.config.ts` manifest 显式声明
  `content_security_policy.extension_pages = "script-src 'self' 'wasm-unsafe-eval'; object-src 'self'"`
  （仅放开 wasm 编译，不含 JS eval 语义，老大已批准）。此修法对真实 Chrome 同样必要。

### CSP 复现实验的意外收获：bug 只存在于生产产物

老大手测「禁用 CSP 修复 + dev 下保存带 import 的脚本」→ 构建成功，看似推翻 E2E 结论。
实查 WXT 源码（`wxt/dist/core/utils/manifest.mjs`）：`addDevModeCsp` 只在
`command === "serve"`（dev）时注入含 `'wasm-unsafe-eval'` 的默认 MV3 CSP，
**生产 build 不注入**。即 dev 下这条链路从未坏过（解释了此前手测一直正常），
bug 只暴露在 `npm run build` 产物上——E2E 跑生产产物所以先撞上。dev 无法复现此问题。
CSP 修复已恢复并重建，冒烟 6/6 仍绿；wxt.config.ts 注释已补记该 WXT 行为。

### CSP bug 真机复现确认（双环境实锤）

老大加载禁用修复的生产产物（CSP=None）到真机 Chrome：**新建脚本即报**
"WebAssembly.instantiateStreaming ... violates CSP: script-src 'self'"。两个要点：

- 与 E2E（Chromium 153 无头）报错一致，bug 双环境实锤；
- **生产下 create 链路也走 esbuild**——与 09-14 日志「新建不跑 esbuild」的记录不符
  （可能指 dev 路径或后来链路变了），影响面比预想大：生产产物上连建脚本都建不了。

修复已恢复重建（生产 manifest 确认含 'wasm-unsafe-eval'），冒烟 6/6、typecheck 仍绿。
