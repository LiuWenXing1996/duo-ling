**#8 实测（真实链路，探针在 `tmp/chunk-probe.spec.ts`，不入库）**：mock OpenAI 兼容 SSE 服务（2ms 间隔推 3000 个 content delta ≈ 24KB，模拟「生成一个大脚本」的最坏节奏）→ 播种模型配置指向 mock → 真实 sidepanel 输入框发送 → 面板内探针记录 chunk 到达时刻 + rAF 长帧统计。

- 结果：3007 chunk 全部到达（7.6 秒流完），间隔 avg 2.5ms / p50 2.5ms / p95 3.3ms / max 106.7ms，>32ms 长帧仅 3 个。
- 结论：**逐条推送的开销远低于可感知掉帧阈值，无需改批量**——维持现状设计。

**坑（Node mock SSE 一行都吐不出）**：探针第一版卡死在「收到 start 后永远等不到后续」——mock 服务里 `req.on('close', () => clearInterval(timer))` 是元凶：新版 Node 的 `IncomingMessage` `close` 事件在**请求体读完时**就触发（不再等连接断开），流式计时器刚起就被清掉。清理必须挂 `res.on('close')`。详见 [lessons.md](../lessons.md)。

## 用户脚本 zip 导入导出（分享语义）开工

**依据**：方案定稿 v1（[userscript-zip-transfer.md](../userscript-zip-transfer.md)）零待拍板项，roadmap #4 开工；轻量提案 [`docs/proposals/done/userscript-zip-transfer.md`](../proposals/done/userscript-zip-transfer.md)（实施层决策见其决策记录，本篇不复述）。

**实施层拍板**（会话中逐条过，共 5 项）：后端解码（offscreen）/ matches 校验器进 `project-store.ts` 与启用路径共用 / 导入撞名保留原名（修订定稿默认值）/ 导出确认弹窗每行+全部都弹 / 拖拽导入 v1 不做。

**写路径走法**（导入怎么过单写方红线）：UI 读 zip 转 base64 → `userscript:import`（SW 纯转发）→ `state:import` → `project-write.importScriptsZip`——解码、解析（zip slip 第一道闸）、`validateMatchPatterns` / `validateFiles`（第二道闸）、构建、落盘、git 快照全在 offscreen 一处；enabled 恒 false，SW 无注册动作。

**坑**：

1. **fflate 的 `zipSync` 遇到字符串 value 会按嵌套 zip 树递归展开，直接爆栈**（RangeError: Maximum call stack size exceeded）——条目值必须全部 `strToU8()` 包好，纯字符串会被当成子树逐字符迭代。
2. **fflate 的 `zipSync` 无法写入含 `..` 段的条目名**（路径展开同样递归爆栈）——好消息：正常导出路径天然产不出 zip slip 恶意条目；恶意样例 zip 得用 Python `zipfile` 造（探针 `tmp/zip-transfer-probe.mjs` 已如此处理）。
3. `npm install` 之后 `.wxt/` 生成目录可能缺席（`tsconfig.json` extends 它），typecheck 会报一堆 moduleResolution / downlevelIteration 假错误——`npx wxt prepare` 重新生成即恢复。

**边界**：notes 档案（提案③ #5）、脚本市场、拖拽导入、多选批量导出均不在本批；`data/` 位恒空（备份语义后置）。

## zip 导入准入语义修订：只拦原则项、尽量导入（取代上一条的闸门描述）

**决定**：「不是原则项的阻断，尽量导入脚本，剩余的都可以走脚本编辑修复。」

| 闸门 | 改前 | 改后 |
| --- | --- | --- |
| 路径不安全（zip slip） | 整脚本跳过 | **只过滤该文件**（进报告「未导入的文件」），脚本其余文件照常导入 |
| 构建失败 | 跳过不落盘 | **仍落盘**（`bundle` 缺省）+ 报告提示带 esbuild 诊断 |
| 版本 `v` | `v > 1` / 缺失 / 非法 → 跳过 | 不校验（开发期无版本规范） |
| `matches` 非法 | 导入时即拦 | 不拦，原样落库（启用时报错） |
| `name` / `entry` / `config` 缺失 | 跳过 | 补默认（目录名 / `main.js` / 逐字段）+ 报告提示 |
| `files` 空、`entry` 不在 `files` | 跳过 | 放行（构建期失败由写侧容忍） |

**唯一保留的原则项**：无可解析的 `project.json`（缺失 / 非合法 JSON / 非对象）——没有 manifest 就构造不出记录。

**为何不破坏既有不变量**：`ScriptProject.bundle` 本就是可选字段；`resolveInjectCode` 在无产物时抛错 → 记 `register` 警告，**绝不会把未构建源码注入页面**，「无产物落盘」只影响该脚本自身且启用时能引导去编辑器修。matches 校验器仍留在启用路径，用户带「哪条规则不合法」去改。

**报告形状**：`ImportItemOk.notes?: string[]`（琥珀色提示，承载构建失败与字段兜底）；「被忽略」区改称「以下文件未导入」并纳入被过滤文件；`ImportItemFailed` 只剩结构性原因。

**测试**：解码层与写侧的旧断言（版本跳过 / 整目录拒绝 / 构建失败出局 / matches 拦截）全部改写为新语义，新增「未导入文件汇进报告」用例；289 例全绿。

## 脚本列表新增「全部删除」（删除全部用户脚本）

**范围**（老大拍板）：只删**新形态用户脚本**——状态库项目 + 各自 git 仓。**不含**已弃用旧 GM 记录（存 `chrome.storage` 的 `us:script:*`，不是项目形态，保留逐行删除与 `userscript:clearDeprecated` 两条既有路径）与内置件（随扩展包分发、不在状态库）。

**命令对**：`userscript:removeAll`（扩展页 → SW）+ `state:removeAll`（SW → offscreen）。删除是写操作，按单写方红线落 offscreen：`removeAllProjects` = ① 记录逐条 `removeProject`；② 仓**整目录清一次** `/uscripts`（不逐条 `deleteRepo`——状态库已空时剩下的目录都是无主仓，整目录清顺带收走滞留仓，判据与启动对账 `reconcileFs` 同源，故在 `us-git` 加 `deleteAllRepos`）。SW 侧另有前后两步：先 `unregisterScripts(全部 uuid)`，落盘后清各脚本 `DL.store` 值（uuid 由 SW 直读状态库，不经容器）。

**交互**：header「全部导出」旁加「全部删除」（ghost + hover 破坏色，无脚本时禁用）；点开确认弹窗明示「将删除全部 N 个脚本，各自 git 历史一并删除 / 此操作不可撤销 / 已弃用旧记录与内置脚本不受影响」。删完逐个广播 `deleted`，宿主据此关掉它们开着的编辑器 / 产物标签。

**不做整批回滚**：中途失败把异常抛给调用方，已删的不复原；操作幂等，重试即可（空库调用返回 0）。

**测试**：新增 `removeAllProjects` 两条用例（批量删 / 空库 0）；`state:removeAll` 登记进 `offscreen-commands.test.ts` 的分发全覆盖表与 `extension-ipc.test.ts` 的 kind 归属表（两张表都有 typecheck 级穷尽断言，漏登记即编译失败）；294 例全绿。
