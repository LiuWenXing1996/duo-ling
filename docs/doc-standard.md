# 文档规范

> 面向「写文档的人 / AI」。代码风格见 [style.md](style.md)，协作与分支流程见 AGENTS.md。
> 本文件只管**文档写成什么样、往哪放**——一句话：**内容规则**。
>
> **与 [proposal-process.md](proposal-process.md) 的分工**：那边管**一件事的生命周期**（五态状态机、流转记录、提案不可删、提案文档怎么写），**自包含、不外链**；这边管**所有其他文档**写成什么样（归属、时态、水文清单、字数上限）。唯一重叠处是提案完成后「事实怎么沉淀成常青篇」，见 §3。
> 想法收集箱是**第三套东西**，见 [ideas.md](ideas.md)，与这两份都只在「提案来源」一个字段上碰头。

## 1. 一个事实只有一个家

同一件事只在一处展开，其余一律链接过去。分类与归属：

| 类型 | 放在哪 | 不该放这的 |
| --- | --- | --- |
| 现在怎么做（规范、用法、契约） | `docs/` 下的常青篇，**就地改** | 变更史、方案讨论 |
| 为什么这么定（仍生效的约定） | `docs/dev-log/conventions.md` | 与 `docs/` 重复的第二遍复述 |
| 讨论过但**决定不做**（没进提案流程的小决策） | `conventions.md`「已否决方案」表 | 埋在方案文档正文里、只写结论不写理由 |
| **想法**（只描述问题） | 想法收集箱，见 [ideas.md](ideas.md) | 在想法里写方案 |
| **提案**（任何变更的依据） | `docs/proposals/<状态>/`，**不可删** | 删掉 / 改历史流转记录 |
| **被拒绝的提案** | `docs/proposals/rejected/`，永久保留 | 抄进 `conventions.md` 否决表（二选一即可，不两边写） |
| 今天干了啥、待拍板 | `docs/dev-log/YYYY-MM-DD.md`，按日追加 | 长期有效的规范 |
| 待办与未落地方案 | `docs/todo.md`（只留索引 + 链接） | 方案全文（→ 提案） |
| 踩坑记录 | `docs/lessons.md` | 排查过程流水账 |
| 已落地的方案 | 提案留在 `done/`；其中的事实抄进常青篇（见 §3） | 继续留在 `docs/` 根目录当正文 |

写之前先问：**换台机器、半年后还要读吗？** 要 → 常青篇；不要 → dev-log 或删。

## 2. 写当前状态，不写变更史

文档陈述**现在是什么样**，不记录**怎么变成这样的**。

- 禁写「原本…现在已移除」「之前用 X，后来改成 Y」「2026-09-15 已修复」——这类留给 git 与 commit message。
- 禁写 PR 号、commit hash、分支名作为正文事实。
- 需要保留决策理由时，写进 `dev-log/conventions.md` 并用一句话点明结论，不复述过程。

例外（不受此限）：

- `dev-log/` 按日流水本身就是时序记录。
- **提案文档的「流转记录」**——它是提案的固有属性，不是变更史。

## 3. 提案完成后：事实沉淀成常青篇

> 提案文档怎么写、状态怎么流转 → [proposal-process.md](proposal-process.md)，那边自包含，本文件不复述。
> 本节只管**提案进了 `done/` 之后，里面的东西怎么变成常青文档**。

提案进 `done/` 即终态、**原文永久保留**。但其中的**事实**要沉淀成常青篇，否则后来者得去翻历史提案才知道现在系统怎么工作：

提案进入 `done/` 即终态、**原文永久保留**。但其中的**事实**要沉淀成常青篇，否则后来者得去翻历史提案才知道现在怎么工作：

| 成分 | 典型长相 | 去向 |
| --- | --- | --- |
| 现状事实（契约） | 「写只归 offscreen」「草稿 = git 工作区未提交改动」 | 抄进对应常青篇，改成陈述式 |
| 设计论证（为什么） | 「权衡了 X 与 Y，选 Y 因为…」 | `dev-log/conventions.md`，只留结论 |
| 背景与动机 / 流转记录 | — | **留在提案里**，它是历史记录，不删 |

沉淀出去的常青篇必须**陈述现在是什么样**：现在时、无状态块、不写变更史（§2）。

`todo.md` 只做索引：条目完成后压缩成一行 + 链接，方案全文不留在这里（另见 §5 字数上限）。

## 4. 水文清单（自查用）

写完后逐条对照，中一条就改：

- 同一条规则在两处出现 → 保留一处，另一处改为链接
- 变更史与流水账：「原本」「现在」「已移除」「已重命名」、PR 号、commit hash
- 状态标注散落在正文里（「已实现！」「TODO: 未来做」）——状态由代码和 `todo.md` 承载
- 手工复述代码里的清单（命令表、配置项表、文件树）——源头能生成的就去源头看
- 推理过程：一步步实现叙述、分支证明、测试走查 → 只留结论
- 段落墙：一段塞了多条规则加括号补充 → 拆开
- 强调通胀：满篇加粗、「必须」「千万注意」→ 等于没有重点
- 已落地方案里的未来时（「应该…」「计划…」）

## 5. 软性字数上限

只对**会持续膨胀**的文档设顶，超出时按「搬迁 → 压缩 → 提额」顺序处理，不要直接提额：

| 文档 | 上限 | 说明 |
| --- | --- | --- |
| `docs/todo.md` | 4000 字 | 超出说明方案正文没拆走，见 §3 |
| `docs/lessons.md` | 3000 字 | 超出说明踩坑记录没提炼 |
| `docs/dev-log/YYYY-MM-DD.md` | 单日 1500 字 | 超出说明有内容该进常青篇 |

`AGENTS.md` 不设上限，但每加一节先问：这条是**每次会话都要读**的常驻命令吗？不是就搬到对应文档去链。

## 6. 链接

- 一律用**仓库内相对路径**（`[style](style.md)`、`[总表](../AGENTS.md)`），禁止裸文件名或「见上文」。
- 带锚点的链接（`#xxx`）改标题时必须同步改，否则变死链。
- 发现死链、过时内容、规范互相打架 → 直接说，不用等问。

## 7. 隐私

落盘前一律脱敏，规则见 AGENTS.md「全局约束 → 隐私与脱敏规则」（不在此复述）。
