# AI 生成后续功能路线图（roadmap）

> 状态：实施完成
> 来源：
> 提案人：

## 问题

一期主链路已落地，剩下的十项未做项 + 一项独立项分散在四处，**没有任何一张图能看清「有哪几件事、各自该开哪个提案、先做谁、依赖什么」**：

- 散在 `docs/userscript-ai-generation.md`（页面上下文档位与拾取器设计、「明确不做」清单、可代定项、逐条推送风险）；
- 散在 `docs/todo.md`——而它的方向是**最终移除**（依据 `docs/proposals/done/idea-inbox.md` 的方向声明），这些条目**没有承接去处**，`docs/inbox.md` 待办里已如实记下这一缺口；
- 已是独立方案稿：`docs/userscript-zip-transfer.md`（方案定稿 v1）、`docs/userscript-page-relay.md`（规范稿 v1，待评审）；
- 散在 `docs/userscript-v2-plan.md` 的 Phase 4。

三个直接后果：想推进时不知从哪项起手；同一件事可能被两个提案各做一半；依赖关系（如拾取器需要一个内置项目承载）只有读完全部文档的人才知道。

另有一条硬约束：`docs/todo.md` 的方向是最终移除，**本路线图不接管它的条目**——否则等于把要拆的东西换个地方重建。

## 方案

新建 `docs/userscript-ai-generation-next.md`，作为「AI 生成后续功能」的**唯一索引**。它只回答四个问题：**有哪几件事、各自该开哪个提案、依赖什么、先做谁**；每项功能的方案全文留在各自提案里，本图每项只留一行链接。

### 归属论证（为什么是三案，不是十案或一案）

判据：「一件事 = 一个能独立说清『改完了没』的变更」「同一份文件 + 同一套验收方式 → 不再拆」「必须同时改才自洽的两半 → 不许拆」。

- **提案 ①「元素拾取器」单独成案**：它跨四层（内置脚本项目 → DL 桥新命令 → 侧边栏拾取入口 → 载荷形态），验收是「用户点选元素后，AI 拿到真实选择器与同类计数」——与其余各项没有交集；它也是唯一改动 DL 桥契约的一项，与只动 offscreen / UI 的 ② 不同批文件。**#10 档 1 / 档 3 页面探针同属「页面上下文」这一面，并入本批**；**#6「内置」分组也归这一案（已定切法 A）**（它是拾取器的前置；两种切法见下节）。
- **提案 ②「生成体验完善」**（#2 进度通知 / #3 消息排队 / #7 regenerate / #8 推送实测 / #9 运行期反馈闭环）：五项都在「已有一次生成会话」的前提下改体验，改动面同批（`offscreen-chat/`、`extension-chat-transport.ts`、`extension-ipc.ts`、侧边栏组件），验收方式同为「面板上可观察的行为」；#8 是实测项（结论可能是「不用改」），#9 是生成-反馈闭环的第二段（用户触发入口 → 新会话带上下文），与其余各项同属一次体验打磨，合批验收更省。
- **提案 ③「脚本资产流转」**（#4 zip / #5 notes）：这一案的内聚不是「文件相同」，而是**都在扩展脚本库这个资产面上——进出的通道（zip）、档案（notes）**，验收方式同为「列表 / 管理页的可观察结果」；#4 已有定稿方案、#5 是小增量，同批可一次把管理页口径理顺。
- **不合成一案**：十项里有三项（#1 拾取器、#4 zip、#8 实测）各带独立前置决策（DL 桥契约、`fflate` 依赖、是否换通道），合成一案会让验收标准无法逐条勾选，也违反「一个 PR 装不下就拆提案」。

### #6「内置」分组归属——定切法 A（两种切法并列留档）

| 切法 | 主张 | 代价 |
| --- | --- | --- |
| **A. 整项归「元素拾取器」提案**（架构师的判定） | 「内置」这个概念是为拾取器引入的（zip / notes 都不需要它），且它是拾取器的**前置**——跨提案前置会把拾取器卡住 | ① 的验收面从「AI 拿到真实选择器」扩到「管理页出现内置分组」，① 变大（但仍在「能独立说清改完了没」的范围内） |
| **B. 拾取器只带最小承载，完整分组体验归「脚本资产流转」提案**（本路线图起草时的建议） | ① 保持最小（只做拾取器功能上必需的承载）；完整分类体验与 zip / notes 同属管理页资产面，同批做省一次改动 | 「内置」概念在 ① 里以「最小承载」先行落地，等于跨提案前置的一半——读者要读两个提案才知道内置脚本最终长什么样；且若 ③ 迟迟不做，管理页会长期只有一个半成品分组 |

**分歧点**：#6 算「① 的组成部分」还是「③ 的组成部分」——实质是**要不要为了「不把前置拆到两个提案」而接受 ① 变大**。

**定：切法 A**——跨提案前置本身是风险，切法 B 的收益「省一次管理页改动」不足以抵。代价一并认下：**① 的验收面从「AI 拿到真实选择器」扩到「管理页出现内置分组」**；若担心 ① 过大，把「内置」分组的**完整 UI 体验**作为 ① 内部的可选后置项，仍留在 ① 里，不拆去 ③。上表两种切法与各自代价作为留档保留。

### 开工顺序（建议）

建议 **① → ② → ③**，理由：

1. **① 先开工**：它决定生成质量的上限（AI 现在只能凭 URL 猜选择器），且它有两个待定设计（载荷形态、回传通道）需要一轮评审——**周期最长，早开工才不压后面的进度**。
2. **③ 中的 zip（#4）随时可插队**：它是唯一「方案已定稿、无待定设计」的一项，卡点只剩 `fflate` 依赖点头；若用户希望尽快拿到分享能力，可把它前插到 ① 之前（它与 ① 的文件冲突面最小）。
3. **② 最后**：五项都是低风险小增量，但它们与 ① 都要动侧边栏 / offscreen 一侧的文件，串行可避免同文件反复冲突。
4. **独立项 `DL.page`** 保持原节奏（规范稿先评审，实施随 v2 Phase 4），本图只记一行，不排期。

### 与其它文档的边界

- **不接管 `docs/todo.md` 的条目**：`todo.md` 的方向是最终移除，本图是它的承接去处之一、但不是它的副本——本图只记「有哪几件事 + 归属 + 顺序」，条目的原表述留在 `todo.md` 直到那次移除提案处理。`todo.md` 留**一行**指向本图的链接（只加链接、不加条目内容）。
- **不写方案全文**：每项功能的方案写在各自提案里；本图每项只给「问题一句话 + 归属 + 依赖 + 依据链接」。
- **不承诺排期**：只给顺序建议与依赖，不给日期。
- **原档「明确不做（本期）」清单里下列几项属有意不收**：**SW 化 esbuild**（原 §3.1 已否）、工具侧 `applyIntents` 链路（老大决策：不用管）——本图不列；**首条 `script_spec` 规范载荷的形态**（原 §6.2 #11）已由现状篇「`script_spec` 约束清单」落地（实现见 `src/lib/offscreen-chat/spec-text.ts`），不再列为未做项。
