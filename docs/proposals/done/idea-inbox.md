# 建立想法收件箱 docs/inbox.md

> 状态：实施完成  
> 来源：  

## 问题

现在没有地方能放「只有问题、还没想好怎么做」的东西。

- 想到什么要么憋着，要么当场摊成方案——逼着自己在问题还没看清时就做设计决策
- 载体缺位是既成事实、不是推测：`AGENTS.md` 文档总表、`doc-standard.md` 的开头说明与归属表，三处都写着「想法收集箱见 `ideas.md`」
- 而 `docs/ideas.md` 在仓库里并不存在——三处全是死链。载体被建过又没了，现在连「该往哪扔」都没答案

判据是清楚的：**有没有方案**。有方案的进 `docs/proposals/`，没方案的现在无处可放。

## 方案

新建 `docs/inbox.md`，规范写在文件开头，下面是「待办」「不办」两个分区。

### 规则

1. 每条 ≤100 字，只写「谁在什么场景遇到什么问题」
2. **不写方案**——写出来说明已经处理过了，那该去 `docs/proposals/`
3. 不排序、不排期、不承诺
4. 进「待办」不代表要做，只表示「这确实是个问题」
5. 移到「不办」必须附一句理由，不许默默删掉
6. **AI 只记不办**：AI 不把「待办」分区当任务清单执行；碰到值得记的念头可以主动问用户要不要加入，但不准不经确认就落笔

### 与 `docs/todo.md` 的关系

方向声明：**最终形态只保留 `docs/inbox.md`**，本提案不动 `docs/todo.md`。移除它属独立变更、**须另开提案**——包括它里面已定稿方案的去处（方案全文按本提案的规则进不了 inbox，得另找家），以及它现有的引用：**规范类 5 处**（`AGENTS.md` 1 处、`doc-standard.md` 4 处），另有若干篇文档散落引用（`plugin-migration-plan.md`、`userscript-single-writer.md`、`testing-plan.md`、`dev-log/`）。不写精确总数——散落引用会随日常改动增减，写死就会过期。

方向声明**不写进 `doc-standard.md`**：它是「还没发生的事」，写进常青篇违反其 §2（不写变更史）与 §4（禁未来时）。它的家在提案里。

### 与 `docs/dev-log/` 的边界

两者都能装「还没做的事」，按**时间尺度**分：`dev-log/YYYY-MM-DD.md` 装当天 / 近期待决的（今天干了啥、待拍板），inbox 装长期未决、且还没方案的。近期待决的会随当天流水自然收口，不该长期挂在 inbox 里占位。

### 膨胀处理

它明确是会持续增长的文档，纳入 `doc-standard.md` 的软上限表（3000 字）。超了按「清掉已升级成提案的条目 → 合并重复条目 → 提额」的顺序处理，不直接提额。

### 自动校验

新增 `scripts/check-inbox.py`（npm 命令 `check:inbox`），与 `check:proposals` 平级、互不依赖——提案检查管的是提案流程，这个是 inbox 的条目规则，两者不是一回事，不合并也不互相调用。

检查四项：

1. 单条 >100 字
2. `inbox.md` 总字数 >3000
3. 「不办」条目缺「理由：」前缀
4. 疑似重复条目：去掉标点与空白后，两条完全相同、或一条是另一条的子串即报

第 4 项是给膨胀处理第二步补工具——inbox 会持续增长，重复就是膨胀主因，而「合并重复条目」原本没有检查兜着。

提醒级：有问题退出码 1，**不进 CI**（与 `check:proposals` 现状一致，都由人按需跑）。

**触发点**：脚本不进 CI，就得写清楚谁在什么时候跑，否则等于没设：

1. `docs/inbox.md` 顶部写明「改完跑 `npm run check:inbox`」
2. `AGENTS.md` 常用命令表该行注明「整理 inbox 时跑」
3. 文档里提示跑 `check:proposals` 的地方顺手带上它——仅文档并列，脚本互不调用

**脚本查不了的一条**：「AI 不擅自写入」只能靠流程守——AI 与人共用 git 身份，脚本区分不了写入方。

### 实施动作

1. 创建 `docs/inbox.md`（两个分区留空，顶部带触发提示）
2. 新增 `scripts/check-inbox.py` 与 npm 命令 `check:inbox`
3. `AGENTS.md` 文档总表新增一行指向 `docs/inbox.md`，文案写明「这里没有方案、不承诺要做」
4. 三处 `ideas.md` 死链改指向 `inbox.md`：`AGENTS.md` 文档总表 1 处；`doc-standard.md` 开头说明 1 处、§1 归属表 1 处
5. 与第 4 条**同一行**、别当两件事：`doc-standard.md` 开头那句在改链接的同时**删掉「与这两份都只在『提案来源』一个字段上碰头」半句**——本提案不再设这个接口，留着是错的
6. `doc-standard.md` 软上限表新增 `docs/inbox.md` 3000 字一行，并在该行注明「由 `check:inbox` 查」——该表其余上限都靠人自查，不注明就成了「设了上限没人查」的空文
7. `AGENTS.md` 常用命令表新增 `check:inbox` 一行，注明「整理 inbox 时跑」

### 收件箱长什么样

仅示意格式：实施时把上面「规则」小节的原文填入 `## 规则`，两个分区初始留空，顶部带触发提示。

```markdown
# 想法收件箱

> 改动后跑 `npm run check:inbox`。

## 规则

<!-- 此处写规则原文 -->

## 待办

<!-- 初始为空 -->

## 不办

- 一句话描述这个想法 —— 理由：一句话说明为什么不办
```

## 备选方案

- **GitHub Issues + `idea` 标签**：外部贡献者能提、天然可讨论。但想法该是「低成本扔进来」的东西，走 Issue 要建号、选标签、想标题，门槛反而更高；且 AI 得联网调 `gh` 才能读写，离线时记不下来
- **`docs/ideas.md`**：与 `proposals/` 平行、直白。但「ideas」不带处理状态，容易被写成「想法的正式清单」，正是 todo.md 走过的老路
- **一条想法一个文件（`docs/ideas/` 目录）**：检索和链接方便，但把「随手写一句」变成「新建一个文件」，抬高了扔东西进来的成本
- **`docs/todo.md` 加个分区**：一个文件搞定、不用新建载体。但它**只有「待办」没有「不办」**——名字就写死了「这是要做的事」，装不下「想清楚了但不做」的条目；而「待办 / 不办」成对才构成处理状态，正是 `ideas.md` 输掉的同一个理由
- **不建载体，想法直接开提案**：等于要求每个想法诞生时就得有方案，与问题本身矛盾

## 不做的事

- 不动 `docs/todo.md`：本次既不迁移它的内容，也不删它——那是另一篇提案的事（见方向声明）
- 不在 inbox 里写方案、排期、优先级
- 不把 inbox 做成提案的前置队列
- 不给 inbox 与提案之间设结构化链接——两者互不引用
