# 建立想法收件箱 docs/inbox.md

> 状态：草稿  
> 来源：  
> 提案人：[LiuWenXing1996](https://github.com/LiuWenXing1996) + AI

## 问题

现在没有地方能放「只有问题、还没想好怎么做」的东西。

- 想到什么要么憋着，要么当场摊成方案——逼着自己在问题还没看清时就做设计决策
- 历史上这些半成品混进了 `docs/todo.md`，于是它里面既有已落地的实现细节、又有方案定稿的全文，谁也看不出哪条其实只是个念头

判据是清楚的：**有没有方案**。有方案的进 `docs/proposals/`，没方案的现在无处可放。

## 方案

新建 `docs/inbox.md`，规范写在文件开头，下面是「待办」「不办」两个分区。五条规则：

1. 每条 ≤100 字，只写「谁在什么场景遇到什么问题」
2. **不写方案**——写出来说明已经处理过了，那该去 `docs/proposals/`
3. 不排序、不排期、不承诺
4. 进「待办」不代表要做，只表示「这确实是个问题」
5. 移到「不办」必须附一句理由，不许默默删掉

与提案体系之间**只有一个接口**：提案的「来源」字段可以填 inbox 里某条的锚点。不要求每个想法都升级成提案，也不要求每个提案都有对应想法。

实施动作：创建 `docs/inbox.md`；在 `AGENTS.md` 文档总表加一行指向它；删掉未跟踪的 `docs/ideas.md`（其内容指向已否决的 GitHub Issues 方案，与本次结论冲突）。

收件箱长这样（示例）：

```markdown
# 想法收件箱

> 这里只放「只有问题、还没想好怎么做」的东西。每条 ≤100 字，只写谁在什么场景遇到什么问题，不写方案、不排期、不承诺。

## 待办

- 弹窗里粘贴大段文本偶尔丢最后几个字符（场景：从备忘录拖拽进来），待确认是否必现
- 配置页搜索框在暗色模式下对比度太低，看不清

## 不办

- 给每个想法自动生成标签 —— 太早分类反而抬高扔进来的门槛，等真要找时再人工归
```

注意「不办」那条自带理由（「太早分类反而抬高门槛」）——这正是第 5 条规则要求的，删条目必须说清为什么，不许默默消失。

## 备选方案

- **GitHub Issues + `idea` 标签**：外部贡献者能提、天然可讨论。但想法该是「低成本扔进来」的东西，走 Issue 要建号、选标签、想标题，门槛反而更高；且 AI 得联网调 `gh` 才能读写，离线时记不下来
- **`docs/ideas.md`**：与 `proposals/` 平行、直白。但「ideas」不带处理状态，容易被写成「想法的正式清单」，正是 todo.md 走过的老路
- **一条想法一个文件（`docs/ideas/` 目录）**：检索和链接方便，但把「随手写一句」变成「新建一个文件」，抬高了扔东西进来的成本
- **不建载体，想法直接开提案**：等于要求每个想法诞生时就得有方案，与问题本身矛盾

## 验收标准

- [ ] `docs/inbox.md` 已创建：开头是五条规则，下面是「待办」「不办」两个分区
- [ ] 「不办」分区的条目带理由字段，示例一条
- [ ] `AGENTS.md` 文档总表新增一行指向 `docs/inbox.md`
- [ ] 未跟踪的 `docs/ideas.md` 已删除
- [ ] `npm run check:proposals` 通过（本提案状态标记与目录一致）

## 不做的事

- 不迁移 `docs/todo.md` 的任何内容——它里面六条全都有方案，属提案范畴，须另开提案
- 不在 inbox 里写方案、排期、优先级
- 不把 inbox 做成提案的前置队列
