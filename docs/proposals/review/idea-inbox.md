# 建立想法收件箱 docs/inbox.md

> 状态：评审中  
> 来源：  
> 提案人：[LiuWenXing1996](https://github.com/LiuWenXing1996) + AI

## 问题

现在没有地方能放「只有问题、还没想好怎么做」的东西。

- 想到什么要么憋着，要么当场摊成方案——逼着自己在问题还没看清时就做设计决策
- 载体缺位是既成事实、不是推测：`AGENTS.md` 文档总表、`doc-standard.md` 开头说明、`doc-standard.md` 归属表三处都写着「想法收集箱见 ideas.md」，而 `docs/ideas.md` 在仓库里不存在——三处全是死链。载体被建过又没了，现在连「该往哪扔」都没答案

判据是清楚的：**有没有方案**。有方案的进 `docs/proposals/`，没方案的现在无处可放。

## 方案

新建 `docs/inbox.md`，规范写在文件开头，下面是「问题」「不办」两个分区。七条规则：

1. 每条 ≤100 字，只写「谁在什么场景遇到什么问题」
2. **不写方案**——写出来说明已经处理过了，那该去 `docs/proposals/`
3. 不排序、不排期、不承诺
4. 进「问题」不代表要做，只表示「这确实是个问题」
5. 移到「不办」必须附一句理由，不许默默删掉
6. **条目不可锚定**：列表项没有 id，提案「来源」引用时写「`inbox.md` 条目：\<首句\>」；条目改写后允许对不上——来源是决策背景，不是硬链接
7. **AI 只记不办**：AI 不把「问题」分区当任务清单执行，只在被要求时往里记

分区名用「问题」而不是「待办」，因为 `docs/todo.md` 就叫待办清单，两个「待办」并存会让文档和 AI 都指不清说的是哪个。

膨胀处理：它明确是会持续增长的文档，纳入 `doc-standard.md` 的软上限表（3000 字）。超了按「清掉已升级成提案的条目 → 合并重复条目 → 提额」的顺序处理，不直接提额。

与提案体系之间**只有一个接口**：提案的「来源」字段可填 inbox 某条（按规则 6 的写法）。不要求每个想法都升级成提案，也不要求每个提案都有对应想法。

实施动作：创建 `docs/inbox.md`；`AGENTS.md` 文档总表加一行指向它；把上述三处 `ideas.md` 死链改指向 `inbox.md`；`doc-standard.md` 软上限表加一行。

收件箱长这样（示例条目全部可在项目中核实，不是虚构场景）：

```markdown
# 想法收件箱

> 只放「只有问题、还没想好怎么做」的东西。规则：
> 1. 每条 ≤100 字，只写谁在什么场景遇到什么问题
> 2. 不写方案——写出来说明已经处理过了，那该去 docs/proposals/
> 3. 不排序、不排期、不承诺
> 4. 进「问题」不代表要做，只表示这确实是个问题
> 5. 移到「不办」必须附一句理由
> 6. 列表项不可锚定，引用时抄首句
> 7. AI 不把「问题」当任务清单执行，只在被要求时记

## 问题

- 同一条归属规则在 AGENTS.md 与 doc-standard.md 各写一遍，改一处漏一处（本次改想法载体就漏了两处引用）
- 提案体检脚本只扫 proposals/ 内部，别处对文档的引用失效了没人发现
- docs/todo.md 里已定稿方案正文太长，「哪条还没开工」要读完才知道

## 不办

- 给想法自动生成标签 —— 太早分类反而抬高扔进来的门槛，等真要找时再人工归
```

注意「不办」那条自带理由（「太早分类反而抬高门槛」）——这正是规则 5 要求的，删条目必须说清为什么，不许默默消失。

## 备选方案

- **GitHub Issues + `idea` 标签**：外部贡献者能提、天然可讨论。但想法该是「低成本扔进来」的东西，走 Issue 要建号、选标签、想标题，门槛反而更高；且 AI 得联网调 `gh` 才能读写，离线时记不下来
- **`docs/ideas.md`**：与 `proposals/` 平行、直白。但「ideas」不带处理状态，容易被写成「想法的正式清单」，正是 todo.md 走过的老路
- **一条想法一个文件（`docs/ideas/` 目录）**：检索和链接方便，但把「随手写一句」变成「新建一个文件」，抬高了扔东西进来的成本
- **不建载体，想法直接开提案**：等于要求每个想法诞生时就得有方案，与问题本身矛盾

## 验收标准

- [ ] `docs/inbox.md` 已创建：开头是七条规则，下面是「问题」「不办」两个分区
- [ ] 「问题」分区的示例条目均可在项目中核实，无编造场景
- [ ] 「不办」分区的示例条目带一句理由，与规则 5 一致
- [ ] `AGENTS.md` 文档总表新增一行指向 `docs/inbox.md`
- [ ] `ideas.md` 的三处死链（`AGENTS.md` 1 处、`doc-standard.md` 2 处）已改指向 `inbox.md`
- [ ] `doc-standard.md` 软上限表新增 `docs/inbox.md` 3000 字一行
- [ ] `npm run check:proposals` 通过（本提案状态标记与目录一致）

## 不做的事

- 不迁移 `docs/todo.md` 的任何内容——它里面的条目都已有方案，属提案范畴，须另开提案
- 不在 inbox 里写方案、排期、优先级
- 不把 inbox 做成提案的前置队列
- 不做自动校验脚本：≤100 字与七条规则靠写的时候自觉，不引入 CI 检查
- 不给条目加 id 或标题——那会把「随手写一句」变成「填表单」，与收件箱的初衷冲突
